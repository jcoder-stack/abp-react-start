## 一句话结论

这套系统的美学判断是成熟的：一个强调色、发丝边框、克制的圆角、字重而非色彩承担层级——这些都站得住，而且执行得比多数同类模板认真。

问题几乎全部收敛到同一个根因：**它是在暗色下设计的，浅色是映射过去的，而映射从未重新验证**。下面 A 档三条是三个互相独立的证据，都指向这一点。

次要的一类问题是：文档把若干**实现细节**论证成了**设计决策**，读起来像深思熟虑，实际是在为现状找理由。

# A 档：合规与可用性

## A1. 浅色主题的文字阶梯，下两级不可用 ✅ 已实施

**现状**：文档定义四级文字阶梯 `foreground` → `muted-foreground` → `foreground-subtle` → `foreground-tertiary`，用途分别是「正文与标题 / 元信息与占位 / 更弱的支持性文字 / 禁用与脚注」，并强调「三级同屏是常态，只有两级会让屏幕摊平」。

**实测**（浅色底 `oklch(0.978 0.001 286)`）：

| 级 | L | 对比度 | 结论 |
| --- | --- | --- | --- |
| foreground | 0.190 | 17.34:1 | 过 |
| muted-foreground | 0.505 | 5.52:1 | 过 |
| foreground-subtle | 0.600 | **3.71:1** | 不过 AA（正文需 4.5） |
| foreground-tertiary | 0.680 | **2.71:1** | 不过，接近不可读 |

暗色下同四级是 17.62 / 6.86 / 5.42 / 3.29——只有最后一级掉线。

**判断**：这不是「调深一点」能解决的。浅色底上正文级文字的 L 上限是 **0.553**（实算），可用区间只有 0.19–0.553，跨度 0.363。要在这段里塞四级**内容**文字，相邻间隔平均 0.12——而现状浅色的间隔是 0.315 / 0.095 / 0.080，后两级已经挤到肉眼分不出，还同时掉出合规线。两头都占不住。

顺带排除一个直觉方案：把页底压暗并不能扩容。bg 从 0.978 压到 0.95，AA 上限也跟着从 0.553 降到 0.534，可用跨度反而从 0.363 缩到 0.344。

**建议**：承认**内容文字只有两级**，第三级是禁用状态（WCAG 对禁用控件豁免对比度），而不是第三级内容。

| 令牌 | 浅色 L | 对比度 | 暗色 L | 对比度 | 动作 |
| --- | --- | --- | --- | --- | --- |
| `foreground` | 0.19 | 17.34:1 | 0.96 | 17.62:1 | 不动 |
| `muted-foreground` | 0.505 | 5.52:1 | 0.68 | 6.86:1 | 不动 |
| `foreground-disabled` | 0.60 | 3.71:1（豁免） | 0.50 | 3.29:1（豁免） | 由 `foreground-subtle` / `foreground-tertiary` 二合一改名 |

**在用的两个颜色一个都不动**，只删一个令牌、给另一个改名；两个新值都是现有值，不用重算。

实施时发现的补充证据：`foreground-subtle` 与 `foreground-tertiary` 在全仓**零调用点**——只在令牌表里定义过，没有任何组件用过。文档为一套产品从未使用的四级阶梯论证了整整一节。

初稿在这里给的是另一个方案：三级内容文字，把 `muted-foreground` 从 0.505 加深到 0.44 以拉开间距。那个方案不好——它为了阶梯的对称，让全站次要文字变深一档，而这套系统的气质恰恰来自「淡」。为排版的对称付这个代价不值。

代价换成了另一处：「更弱的支持性文字」这一档失去灰度。但这跟系统自己的主张对得上——文档反复讲「层级来自间距和字重，不是色彩」，那第三级支持性文字本就该用字号或字重表达。浅色底只能容下两级内容灰度，是这套配色的事实，不是缺陷；只要别在文档里声称有四级。

改名不只是换名字：它把「这级不能承载内容」写进了令牌名，比写在文档里管用。

## A2. 状态药丸在浅色下全部低于 AA ✅ 已实施

**现状**：状态徽标是「`status-*` 文字 + 同色 15% 淡底」。文档为五个状态色列了对比度，但算的是**文字对卡片底**——用户实际看到的是**文字压在自己的淡底上**。

**实测**（文字 / 药丸内底面）：

| 状态 | 浅色药丸内 | 浅色对卡片 | 暗色药丸内 |
| --- | --- | --- | --- |
| success | **3.75:1** | 4.56:1 | 6.46:1 |
| warning | **3.15:1** | **3.74:1** | 7.63:1 |
| error | **4.24:1** | 5.38:1 | 5.07:1 |
| info | **4.01:1** | 4.89:1 | 5.76:1 |
| neutral | **4.03:1** | 4.86:1 | 5.34:1 |

浅色下**五个全部低于 4.5**，而徽标文字是 12px，属于小字，必须 4.5。warning 连对卡片底都只有 3.74——它在任何底面上都不合规。暗色五个全过。

**判断**：淡底吃掉了 0.8–1.2 的对比度，这一步在设计时被跳过了。又是同一个病根：暗色下淡底压在 0.174 的卡片上几乎不改变前景关系，浅色下压在纯白上就把底抬到接近文字。

**建议**：浅色主题的五个状态色压暗到刚好让药丸内达到 4.5:1（实算）：

| 状态 | 现值 L | 建议 L | 药丸内 |
| --- | --- | --- | --- |
| success | 0.55 | **0.500** | 4.50:1 |
| warning | 0.62 | **0.524** | 4.50:1 |
| error | 0.55 | **0.534** | 4.50:1 |
| info | 0.55 | **0.520** | 4.50:1 |
| neutral | 0.55 | **0.521** | 4.50:1 |

色相与彩度不动，只压明度，五个色之间的关系不变。暗色一律不动。

另一个更省事的选项是把淡底从 15% 降到 8–10%，但那会让药丸在浅色下弱到几乎看不出是个药丸——状态是要一眼扫到的东西，不该更淡。建议压明度。

## A3. 暗色下 primary 按钮的白字是 4.47:1 ✅ 已实施

**现状**：文档写「`primary` carries white text at 5.09:1 in light and 4.65:1 in dark」。

**实测**：按**纯白** `#fff` 算，是 5.08 / 4.66——和文档几乎一致，说明作者确实算过。但系统实际的 `primary-foreground` 是 `oklch(0.985 0 0)`，不是纯白。按实际令牌算：**5.08 → 4.87（浅）、4.66 → 4.47（暗）**。

暗色按钮跌破 4.5。差 0.03，但按钮文字是 14px 正文级，这条线两边意义不同。

**判断**：这是全文唯一被明确背书过对比度的地方，而它被一个 1.5% 的明度差掀翻了。值得注意的是 `primary-bright`（5.44 vs 文档 5.48）和焦点环（4.73/5.27，文档说「clears 3:1」）都对得上——所以不是方法错了，是这一组没用实际令牌复核。

**建议**：把 `primary-foreground` 改成纯白 `oklch(1 0 0)`。一行改动，暗色按钮回到 4.66:1，浅色到 5.08:1，与文档已写的数字一致。不要动 `primary` 本身——要靠压暗填充色达标，L 得降到 0.20，那就不是这个蓝了。

## A4. 移动端输入框会触发 iOS 整页放大 ✅ 已实施

**现状**：shadcn 的 `Input` / `Textarea` 原语把类写成 `text-base md:text-sm`。这个 idiom 的全部意义在于阈值——**iOS Safari 在字号小于 16px 的输入框获得焦点时会放大整页，而且放大后不会自己缩回**，用户必须手动捏合。`text-base` 在 Tailwind 默认刻度里正好是 16px，原语靠它兜住移动端，桌面端再用 `md:text-sm` 收回密度。

本主题把 `--text-base` 重定义成 `0.875rem`（14px，密集后台的正文尺度）。类名没变，那道保险却拆掉了：移动端每一个输入框和文本域都是 14px，每次聚焦都放大整页。

**判断**：这是重定义一个**被别人依赖的**刻度名所付出的代价。文档把 `--text-base` 当成自己的正文尺寸在调，没注意到 shadcn 的原语正在用它的默认值当行为开关。这类耦合不会在任何桌面截图里暴露出来。

**已实施**：在主题层按 slot 补回，不 fork 原语——

```css
@media (width < 48rem) {
  [data-slot="input"], [data-slot="textarea"] { font-size: 1rem; }
}
```

实测：375px 视口下 input / textarea 均为 16px，1280px 下仍为 13px，桌面密度不受影响。

另一条路是把 `--text-base` 还原成 16px、恢复这个刻度名的公认含义。没走那条是因为它牵连 B6（见下），应当一起决定，而这个 bug 不该等。

# B 档：体系一致性

## B4. 「一个蓝」是宣言，不是事实 ✅ 已实施

文档至少三处强调 one blue / one job：「the accent never gets diluted across the UI: one blue, one job」。实际有六个蓝令牌：`primary`、`primary-hover`、`primary-bright`、`primary-focus`、`sidebar-primary`、`brand-mark`。

每一个的理由单独看都成立——`primary-bright` 是因为填充色当前景对比度不够，`brand-mark` 是小尺寸的光学补偿，`primary-focus` 是为了不与控件边框糊在一起。问题在于六个之后那句宣言就失效了，而文档仍在用它论证别的决定（比如为什么状态色要独立于强调色）。

**建议**：把叙事从「一个蓝」改成「**一个色相，四种职能**」——填充（`primary` + `hover`）、前景标记（`primary-bright`）、焦点（`primary-focus`）、品牌标识（`brand-mark`）。这样既诚实，又把「什么时候该新增一个蓝」变成可判断的问题：新的蓝必须对应一个新职能，否则就是重复。现在的写法给不出这个判断依据。

## B5. `status-error` 与 `destructive` 的区分只对开发者成立 ✅ 已实施

两者同色相 25、同彩度 0.20，明度差 0.045。文档花了一整段解释它们「不是同一个令牌」，并在 Do's 里立了一条禁令。

但用户看到的是同一个红。真正区分二者的是**形态**——实心按钮 vs 淡色药丸——而形态本来就区分了，不需要颜色再区分一次。这一段读起来像设计决策，实质是在为「令牌表里有两个近似值」这件事补一个理由。

**建议**：要么合并成一个红、由形态承担区分（更干净，少一个令牌）；要么保留两个但把理由改成真实的那个：**药丸底是 15% 淡色，填充按钮是实心，两者对前景对比度的要求不同，所以需要两个明度**——这个理由是成立的，而且 A2 的计算正好支持它。现在写的理由（「一个是状态，一个是动作」）站不住，因为语义差别没有落到任何可感知的视觉差别上。

## B6. 刻度有 11 档，产品只用 3 档 ✅ 已实施（走甲）

相邻比实测：

```
11→12  +9.1%    15→20  +33.3%
12→13  +8.3%    20→24  +20.0%
13→14  +7.7%    24→32  +33.3%
14→15  +7.1%    32→40  +25.0%
```

11–15px 五档总跨度只有 ×1.36，相邻平均 8.1%。UI 里 8% 的字号差（13px 对 14px = 1px）基本不可辨——文档自己也承认了这点，它写「weight does more work than size in this range」。

但真正的证据是用量。全仓 214 处字号类的分布：

| 档位 | 用量 | |
| --- | --- | --- |
| `text-sm` 13px | **113** | 真正的默认 |
| `text-xs` 12px | **45** | |
| `text-2xl` 24px | **27** | 页标题 |
| `text-base` 14px | 7 | ← 文档称「the default UI text, most of the interface is set here」 |
| `text-lg` 15px | 6 | |
| `text-2xs` 11px | 6 | |
| 其余五档 | 各 2–4 | |

**11 档里 3 档承担了 87% 的用量，而文档声称的默认档只有 7 处使用。** 所以问题不是「相邻只差 8%」这种比例洁癖，是**档位设置与实际用途根本没对上**——文档在描述一套不存在的用法，而每个使用点仍要在 11 档里做一次选择。

同时 15→20 是 33% 的断崖，中间没有 17–18px。后果是「比正文大一点的标题」无处可去：卡片标题只能选 15px（与描述同级，靠字重硬撑）或 20px（在 13px 的表格上方显得像页标题）。文档里把浮层标题定在 15px/590 并专门论证「不用 20px」，就是这个断崖的直接产物——它被写成了一个设计主张，实际是刻度缺档逼出来的。

**建议**：把两个几乎无人用的档合并，用省出来的位置填上断崖。

```
11 / 12 / 13 / 14 / 15 / 20 / 24 …   →   11 / 12 / 13 / 15 / 17 / 20 / 24 …
                                          （text-base 14→15，text-lg 15→17）
```

13px 仍是正文基线（113 处不动），下端少一个 7% 的假档位，而卡片标题、浮层标题终于有了「比正文大一档」的真档位（17px）。文档里那段「浮层标题定 15px 而不用 20px」的论证也就不必存在了——它本来就是缺档逼出来的辩解。

**成本**：`@theme` 两个值 × 两份镜像文件，组件一处都不用改（全仓硬编码字号只有 2 处，其余 214 处全走刻度类；这套架构本来就是为了让刻度可换而设计的）。需要复核的是那 13 个 `text-base` / `text-lg` 调用点的观感。

初稿在这里写的是「不建议现在动，会波及全站」。那个判断错了两次：成本估错了（以为要改几百处，实际是改几个值），而且把成本当成了设计理由。

**但上面这个建议同样不能执行。** 实施时逐个看了 `text-base` 的调用点，发现它根本不是「7 处几乎无人用」——其中两处是 `Input` 与 `Textarea` 原语的 `text-base md:text-sm`，而那正是移动端不被 iOS 放大的唯一依靠（见 A4）。**`text-base` 是被原语依赖的行为开关，不是一个闲置档位**，「把两个没人用的档合并」这个前提不成立。14→15 既修不了那个 bug（阈值是 16px），也失去了依据。

于是这条变成一道需要拍板的选择题，两个方向都成立：

- **甲：把 `--text-base` 还原成 16px。** 恢复这个刻度名的公认含义，A4 的主题层补丁也就可以撤掉。代价是 13→16 成为一个 23% 的跳档，营销正文与特性卡标题从 14px 变 16px（这两处本来 16px 更合适），而且 `base`(16) 会大于 `lg`(15)，刻度名不再单调——`lg` 得跟着往上挪到 18px，浮层标题也就从 15px 变 18px，而文档为 15px 专门论证过。
- **乙：维持 14px，保留 A4 的补丁。** 刻度不动，但 `text-base` 这个名字在本系统里就永远和别处不同义，下一个用到它的原语还会踩同一个坑。

**仍然成立的部分**：15→20 的断崖和「11 档只用 3 档」的事实没有变，两个方向都得单独处理它。

**结论：走甲。** 实施如下——

```
11 / 12 / 13 / 14 / 15 / 20 / 24 …   →   11 / 12 / 13 / 16 / 18 / 20 / 24 …
```

- `--text-base` 还原成 **16px**，恢复这个刻度名的公认含义。原语的 `text-base md:text-sm` 自此原生成立，**A4 的主题层补丁已撤除**——实测移动端 375px 下 input 为 16px、桌面 1280px 下为 13px，与打补丁时一致，但不再需要维护一条额外规则。
- `--text-lg` 跟着上移到 **18px**（否则 `base`(16) 大于 `lg`(15)，刻度名不再单调），行高 1.45、字距 -0.012em。它现在是「卡片标题、浮层标题」那一档，front matter 里也从 `body-lg` 改名为 `title-sm`——留着 `body-lg` 这个名字指代一个标题尺寸，正是本条批评 `text-base` 时说的那种「名字在本系统里异义」。
- 14px 与 15px 两个假档位消失。13px 仍是产品基线（全仓约半数），营销正文与移动端表单落到 16px，卡片/浮层标题落到 18px。
- 文档里那段「浮层标题定 15px 而不用 20px」的长篇论证已删除——它本来就是断崖逼出来的辩解，给了刻度真档位之后论证自己就没了。

目测确认：18px/590 的弹窗标题压在 13px 说明文字上读作标题，不读作页标题。

# C 档：叙事与边界

## C7. 表格密度由一个次要控件决定 ✅ 已实施

文档说舒适档行高 48px，并注明「行内操作按钮撑起了下限，纯文本行落在 36px 附近」。也就是说：整张表的密度是由行尾那个 `⋯` 按钮的尺寸决定的，而不是由「一屏要看到多少行」决定的。一个自称密集后台的系统，这是本末倒置。

实测：表头 `h-10` = 40px，行尾操作按钮 `size-8` = 32px。行高的下限就是这个 32px 加上下内距。

**建议**：行高应当由「一屏要看到多少行」决定，然后让控件适配它——**舒适档 40px（与表头对齐），紧凑档 32px，行尾按钮缩到 28px**。成本不高：单元格内距一行 + 按钮尺寸一行（×2 份镜像）。

排在后面不是因为难，是因为它改的是密度观感，不像 A2 那样纯靠计算就能定——需要拿一屏真实数据看过再落值。starter 的数据页需要 ABP 后端（`.env` 指向 `localhost:44316`），无人值守时拿不到真实一屏，所以未实施。

**在真实数据上量到的**（AbpSwagger 后端 + 组件演示的图书表，1440×900）：

| | 改动前 | 改动后 |
| --- | --- | --- |
| 行高（舒适） | 49px | **40px** |
| 行高（紧凑） | 41px | **32px** |
| 十行占高 | 490px | **400px** |
| 单元格纵向内距 | 8px | 0（高度改为声明） |
| 行尾菜单钮 | 32px | 28px |

决定性的证据是逐格量出来的：**整行里唯一高度超过 20px 的元素，就是第 6 列那个行尾菜单钮**，其余每格都是 19px 的文字。8+32+8=48，加边框 49——一张表的密度由一个多数行根本不会去点的控件决定。

修法不是调 padding。把 padding 改小只会得到「文本行 32px、带按钮行 40px」，同一个毛病换个数字重演。实际做法是**把行高声明出来**：单元格纵向内距归零（主题层），密度档位直接给 `[&_td]:h-10` / `[&_td]:h-8`，按钮缩到 28px 以装进两档。密度从涌现值变成定值。

## C8. 「绝不斑马纹」缺少适用条件 ✅ 已实施

现状是一条无条件禁令，理由是「reads busy against the quiet palette」。对窄表这成立。但列数多到需要横向扫视时，取消斑马纹是有代价的——横向追踪错行是宽表的主要错误来源，这也是斑马纹这个惯例存在的原因。

**建议**：给条件。列数 ≤6 用发丝分隔；更宽的表允许 hover 整行高亮 + 主列吸附（文档在响应式一节已经要求主列吸附了，两处可以合并成一条规则）。口味写成禁令，会在真遇到 12 列的表时被整条绕过——那时连发丝分隔的部分也一起丢了。

## C9. 三块空白：无障碍、文案、双语排版

- **无障碍**只在色彩一节零星出现几个对比度数字，没有集中的 AA 承诺、没有键盘导航规范、没有 aria 约定。而 `CLAUDE.md` 里其实有硬规则（必填字段的 `aria-required`、`isError` 分支的强制、焦点可见性），它们没进 DESIGN.md——设计规范和实现规范分居两个文件，评审设计的人看不到。
- **文案**完全没有：错误信息的口吻、空状态的措辞、按钮用动词还是名词、标点。这在一个 CRUD 后台里是高频且高影响的东西。
- **双语排版**只处理了字体与字重（那是这两天刚补的），没有处理规则层：`label-caps` 依赖的 Title Case / 全大写在中文里无意义，中英混排的空格约定、数字与单位的处理都没写。这是个双语产品，这块空白比字体问题更常被撞到。

## C10. 310 行 front matter 挡在人读的内容前——**建议不动**

文档同时服务两个读者：工具（front matter）和人（正文）。初稿建议把令牌表移到附录。复查之后**撤回这个建议**。

**仓库内没有任何程序消费者**：无 `gray-matter` / `js-yaml` / `front-matter` 依赖，`scripts/` 不碰 DESIGN.md，CLI 只在 CSS 注释里提了一句。所有指向它的链接（README ×2、`architecture.md` ×2、`CLAUDE.md` ×4）都是整文件链接，不带锚点。所以「YAML 必须在头部」这个约束在本仓库内不成立。

不动的理由是另外三条：

1. **外部工具是唯一真实风险，且无法证伪。** 这份 YAML 的形状（`colors:` / `typography:` / `components:` 加 `{colors.x}` 交叉引用）是标准的设计令牌导出格式，文档也自称「`export --format css-tailwind` 能直接落地」。消费者在仓库外，查不到也否不掉。
2. **`git blame` 会变脏。** 310 行搬家让每个令牌值的 blame 指向移动提交，而令牌值恰恰是最需要 blame 的东西。`blame -w -C` 能追回去，默认视图不能。
3. **主要收益已经被目录拿走了。** 初稿是在文档还没有目录时写的，当时正文从第 320 行开始且无导航。目录补上之后，剩下的只是原始文件的滚动距离和 diff 噪声。

顺带记一个约束：front matter 必须是文件第一行，所以不可能在它上面加导航——选项是二元的，要么留着靠下面的目录，要么整块搬走，没有中间态。

初稿给的理由（「拆了令牌和理由就分居两处，比现在更糟」）是错的，已作废。

## C11. 圆形图标钮规则只命中了 22 个里的 2 个 ✅ 已实施

实施 C7 时在真实页面上发现的。主题层有条规则把图标钮做成圆形，选择器是 `[data-slot="button"][class*="size-8"]`。但 shadcn 的 `asChild` 会把 Button 的 `data-slot` 换成包裹它的 trigger 的 slot——`dropdown-menu-trigger`、`tooltip-trigger`、`collapsible-trigger`……

实测一屏 22 个图标钮，**只有 2 个是圆的**（`筛选` 和 `刷新`，恰好没被 `asChild` 包裹）。工具栏上「刷新」是圆的，紧挨着的「密度」「列」是 6px 圆角方块，语言、主题、行尾菜单同理。而 DESIGN.md 的 Implementation Status 一直写着「圆形图标钮 shipped」。

**已实施**：改为匹配元素而非 slot，并用 `~=` 取代 `*=`——

```css
button[class~="size-7"], button[class~="size-8"], button[class~="size-9"] { border-radius: 9999px; }
```

`~=` 是必须的：只有裸类 `size-8` 才表示「这个按钮本身是 32×32 的图标钮」，而侧栏行上的 `group-data-[collapsible=icon]:size-8!` 是条件类，展开时那是一整行文字，`*=` 会把它圈成胶囊。实测改后 6 个真·图标钮全部变圆，5 个 224px 宽的带文字侧栏行全部未受影响。

顺带删掉了 `[data-slot="toolbar-control"]` 那条规则——全仓没有任何组件发出这个 slot，是条空转规则；DESIGN.md 里对应的「工具栏按钮 2px 圆角」一行也删了，工具栏上的实际都是圆形图标钮。
